# App is live

`release-cut` uploads a build. This skill runs when the store actually serves it: approved and released, or a staged rollout at 100%. The days between those moments are where the last production edits get forgotten — and an update gate left behind means installed apps never learn the new build exists.

`.ai-os/knowledge/release-surface.md` lists which of these apply here and the command for each:

| Target | Why it moves now and not at the cut |
| --- | --- |
| The release record (for example a release note: live date per platform) | Only now do users have the build. |
| The release tag, pushed | It is the baseline for over-the-air patches. |
| A branch that mirrors what users run ← merge the **release tag** | It mirrors the stores, not the trunk. |
| The in-app update gate (latest build, mode, changelog, store link) | The only way installed apps learn the build exists. |
| The project's other post-release commands | Whatever else this project moves at go-live. |

**Use the project's go-live command when release-surface names one** — it is where the guards live; never hand-edit what it owns. Without one, apply the rules below by hand and print every record before and after.

## Report first, always

Read-only, no confirmation needed:

- Was the release ever cut — is its tag on every repository?
- What each storefront the product sells in actually serves, from the public lookup; consoles lag.
- The gate as it stands, and **which environment host** it lives on.
- How far the mirror branch is behind the tag, and how far the trunk is ahead of it.
- The exact change that would be written.
- On an App Store project with standard workflows (`.asc/workflow.json` generated by ai-os): `asc workflow run phased VERSION:<version>` (read-only) shows the phased-release state; run it before any forced update. Pressing Release (`asc workflow run release`) is the owner's act: under the default `ownerActs: ask` Claude Code prompts the human, and you never answer that prompt; under `deny`, tell the owner the command; under `allow`, only an owner request that names the act authorises it.

Read the store state correctly. App Store Connect's `READY_FOR_DISTRIBUTION` means released and downloadable, not waiting for the Release button; on Google Play the release is live when its track rollout is completed (100%), not when review approves it. The public lookup can lag minutes behind a release: when the console says released and the lookup does not yet, say so and re-check; never report the build as not live on the lookup alone. A platform whose gate already carries this build, version and changelog is done: report it and do not offer it again.

A status question is answered with the report and stops. Applying needs an instruction from the owner in the same turn.

## Ask once, after the report

Never ask what a command can read: check first, then ask only what the report left open, each question carrying its evidence and a recommended answer.

- Use the runtime's picker when it has one (`AskUserQuestion` in Claude Code), so the owner chooses rather than types; otherwise numbered questions, each followed by the recommended answer.
- One round: which platforms (only those the report shows live; a platform the lookup cannot see yet needs the owner's word, and that word is enough for `notify` only: `force` waits until the lookup shows the build in every storefront), the mode (`notify` recommended; `force` and `silent` stated with their effect), and the optional steps in **Then**.
- A second round only when needed: the changelog, and for `force` the owner's word on phased release.
- The changelog comes before any `notify` or `force`: draft it from this version's store release notes, show every item in full, and write nothing until the owner approves the text. `silent` needs none.
- Every production write gets its own confirmation, after its dry run: platform, host, before and after.

## Apply

- **One platform per write**, each with its own confirmation. Stores go live at different times: a platform not yet live waits for a later run.
- Dry run first whenever unsure: the gate is production and the only undo is writing the old values back.
- Show the host before every production write. After it, re-read the live endpoint and report what an installed app now receives, not what was sent.
- Merge the **tag**, never the trunk, into the mirror branch — the trunk is ahead of the shipped build. The mirror moves only when every platform is live.

## Refuse

| Refusal | Why |
| --- | --- |
| The latest or minimum build would go backwards | Almost always a mistyped version. |
| A minimum build above the build going live | Blocks everyone, with nothing to update to. |
| Forcing while any storefront still serves the old version | Strands users. |
| Forcing without the owner's explicit word that phased release is off or the rollout is at 100% | No script can check it; never assume it on their behalf. |
| Notify or force with a changelog not written for this version | The last release's notes on this one is a mislabelled build. |
| A store link that is still a beta link or a placeholder | The update button leads nowhere. |
| The release tag is missing | Going live ahead of the cut — use release-cut. |
| Creating the first gate record for a platform | Deliberate; apps should fail open without one. |

## Forcing is a separate decision

A forced update puts a blocking screen in front of every user below the gate, immediately. It is never part of a routine go-live, and needs all three: live in every storefront; phased release off, confirmed by the owner; the real store link. Phased release plus force is the worst outcome available: the store offers the update to a few percent while everyone else is blocked with nothing to download.

## Boundaries

- Over-the-air patches never touch the gate; it describes store builds only.
- Two version spaces (release train and marketing version) — say which one you mean; the owner usually means what the store shows.
- Re-running converges: identical values write identical values.

## Then

Report what is still open: the other platform, the active-release marker (should already point at the next release), and tracker cards still in review for work this build shipped.

Two optional steps, offered in the question round and run only when chosen:

- **Record.** For each card still in review, check whether its work is in the release tag and say what it still needs; move or close a card only on the owner's word. Update the release record through a pull request; merging it follows the project's merge rule.
- **Clean up.** Delete this run's temporary files (the drafted changelog) and return each repository this run touched to a clean trunk. Never discard uncommitted work: list it and ask. Pruning merged worktrees and branches is the workspace-hygiene skill's job, with its own removal list and yes. Clean-up never touches the gate, tags or store state.
